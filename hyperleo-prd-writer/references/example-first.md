# 示例先行协议（Example First）

## 原则

- 例子即规格：业务规则先用 1–3 个具体例子表达，规则从例子归纳，AC 直接写 GWT。
- 甲方的任务是判断例子对不对，不是描述系统。

## 转换流程

1. 从访谈/概念版提取业务规则（R 编号）。
2. 每条规则生成 1–3 个候选例子（正常路径 + 边界 + 异常）。
3. 让用户确认/修正例子（每轮 ≤3 个问题）。
4. 用户确认后，把例子归纳为规则文本。
5. AC 写 GWT；需要自动化时转 Gherkin。

## 例子模板

```markdown
### 规则 R3 批量导入工单

**示例 3.1**（正常 + 部分失败）
- 输入：CSV 2000 行，其中 5 行缺必填字段
- 预期：成功 1995 / 失败 5；失败报告含行号、字段名、原因；不中断整批

**示例 3.2**（重复）
- 输入：同一批次外部工单号重复 2 行
- 预期：重复行失败，非重复行继续导入
```

## GWT → Gherkin

```gherkin
AC-3.1:
Given 2000 行 CSV，其中 5 行缺必填字段
When 提交导入
Then 30 秒内返回结果页，成功 1995 / 失败 5
And 失败报告含行号、字段名、原因
And 导入不中断
```

## 好例子 vs 坏例子

| 好 | 坏 |
| --- | --- |
| 有具体输入（数量、字段、状态） | 只说「导入时做校验」 |
| 有可判定预期（成功/失败/报错内容） | 只说「体验更好」 |
| 覆盖边界/异常 | 只有正常路径 |
| 可追溯到规则编号 | 孤立片段 |

## 策略型需求兜底

没有交互界面的需求（策略、算法、规则引擎）：

- 用「输入事实集 → 决策输出」的例子表达；
- 无法例化的原则性要求显式标为 `RULE-ONLY`，并给 must/should/may 限定。

## 失败模式与防复发

- AI 自造例子且用户未确认 → 例子必须标注 `[待确认]` / `[已确认]`；未确认不进入落地版。
- 例子过多拖长文档 → 每条规则上限 3 个，高风险规则优先。
- 例子与规则矛盾 → 审核步骤横向检查「规则 ↔ 例子 ↔ AC」一致性。
