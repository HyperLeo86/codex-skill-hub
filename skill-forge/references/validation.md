# A/B 前向测试协议 + 发布门

## 目标

用证据回答：这个技能是否真的改变行为、值得占用 token。

## 步骤

1. **准备**：从契约挑 1–3 个真实任务；每个任务写成与真实用户请求同构的 prompt
2. **A 臂（基线）**：全新上下文的 subagent，无技能执行任务；记录完成率、失败点、token 用量
3. **B 臂（带技能）**：同一任务，prompt 改为 `请使用 /path/to/skill 完成：[任务]`；记录同样指标
4. **对比**：

| 指标 | A 臂 | B 臂 | 达标 |
| --- | --- | --- | --- |
| 任务完成率 | | | B > A 或 B ≥90% |
| 行为改变 | | | B 明显不同 |
| token 增量 | | | 增量换回完成率 |
| 产物质量 | | | 通过契约验收 |

5. **结论**：达标 → 进入回灌；不达标 → 改契约后重测，最多 3 轮

## 单位纪律

- 全部工作量用 agent 单位记录（任务数、轮次、pass 数、候选数），不承诺墙钟时间
- 不编造 A/B 结果；跑不出就标「待验证」

## 发布门（三绿）

1. `check_skill.py <skill-dir> [spec.json]` 全绿
2. 回归账本全绿（无「未修复」条目）
3. A/B 达标，或至少 RED→GREEN 测试通过

三绿不满足，不发布新版本。

## 子代理纪律

- 不给预期答案、不给你的诊断、不给修复建议
- 每次用全新上下文；测试产物用后即清，防止污染下一轮
- 复杂技能用两个独立 subagent 并行跑，交叉验证

## 回归账本格式（references/regressions.md）

```text
## 回归账本（保留最近 10 条）

| 日期 | 场景 | 失败 | 修复 | 状态 |
| --- | --- | --- | --- | --- |
| 2026-08-03 | 空输入 | 生成空摘要 | 增加空输入降级条款 | 已修复 |
```

规则：
- 每次真实使用后追加一行
- 超过 10 条时删除最旧条目（或归档到技能外）
- 升级前必须重跑账本中的全部场景；有状态非「已修复」则阻塞发布

## 反合理化清单

| 借口 | 反驳 |
| --- | --- |
| 「这个技能很简单不用测」 | 简单技能更容易被误触发，A/B 只要 10 分钟 |
| 「失败是用户输入的问题」 | 输入边界属于契约的一部分，写进 failure_modes |
| 「测过一次了」 | 每次升级都要回归，否则无法保证长期可靠 |
| 「脚本看起来没问题」 | 必须跑出确定性结果，不能只靠目测 |
